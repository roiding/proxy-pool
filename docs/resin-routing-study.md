# Resin 架构借鉴：粘性会话与非粘性轮换

日期：2026-11-01。状态：架构研究与设计补充，尚未实现。

研究对象：[Resinat/Resin](https://github.com/Resinat/Resin)，本轮读取的 master 提交为 `5473c7ee495b78e4d7441fb5342b8e8127484de5`。核对范围包括 README、DESIGN、路由、租约、订阅同步、可路由视图、探测、持久化和相关测试源码。没有运行 Resin、执行其脚本或进行性能测量，也没有复制其实现代码。

本文件补充现有管理与服务规划。用户新增需求是：同一个系统同时支持 API 业务的粘性与爬虫业务的持续轮换；这两种行为按下游业务配置，而不是按代理来源强行二选一。

## 1. Resin 实际做了什么

| 机制 | 从源码确认的行为 | 对本项目的启示 |
| --- | --- | --- |
| Platform | 定义过滤范围、分配策略和 StickyTTL，维护独立可路由视图 | 引入业务路由策略，与上游渠道和下游认证分开 |
| Account | 非空时以平台内账号查租约；空账号走随机路由 | 业务会话键必须稳定，但本项目用明确 mode，避免漏传键就静默换 IP |
| 粘性锚点 | 租约保存 NodeHash 和 EgressIP；原节点可用且出口未变时复用 | 区分固定连接和固定出口，不把代理节点地址当出口地址 |
| 同 IP 换节点 | 原节点失效时寻找相同出口的替代节点，保留原到期时间 | 有同出口候选时可恢复路由，不必一坏就换出口 |
| 同 IP 候选耗尽 | 创建新租约，可能选择不同出口，TTL 也重新计算 | 对严格 IP 连续性业务不能照搬；要有拒绝换出口的策略 |
| 非粘性 | 每次 P2C 选择，不创建账号粘性租约；没有跨请求排除上次 IP 的规则 | 随机不等于必换 IP；本项目的爬虫策略需要去重窗口 |
| 选点评分 | 两个随机候选按可比较的近期延迟和出口租约负载打分 | 可以借鉴小样本比较，不每次全池排序；没有同口径数据时不能硬比 |
| 订阅更新 | 拉取/解析在锁外；配置版本、尝试序号检查后更新引用关系 | 避免旧下载覆盖新配置；来源与全局节点分离 |
| 热路径视图 | 平台保存预计算可路由集合，节点变化时更新视图 | 过滤索引可优化，但不能取代本项目的交付前验活和事务检查 |
| 持久化 | 配置强持久化，节点与粘性租约通过 dirty sets 异步写缓存库 | 学习冷热数据分级，不照搬租约弱持久化到严格 CD 和会话绑定 |
| 数据面 | 自己转发 HTTP/SOCKS5/反向代理流量，能记录被动健康和目标延迟 | 本项目只返回代理时拿不到这些信号，不能假装拥有同等可观测性 |

## 2. 两个独立维度，不要再把 API 一词混用

“供应商 API”回答代理从哪里来；“API 业务”回答下游怎么使用代理。前者不决定后者是否粘性。

| 供给来源 | 粘性业务 | 轮换业务 |
| --- | --- | --- |
| 静态上传/URL | 从库存选一个合格连接，绑定会话 | 每次分配选近期未用过的合格连接/出口 |
| API 按需 | 首次建会话时取号，绑定到该会话；必要且获准时才重新取号 | 每次需要新分配时按需取号、验活、去重，不保留可复用库存 |

建议业务模板：`api-sticky` 和 `crawler-rotate`，都可以配置允许的静态源或 API 源。爬虫登录流程也可以使用粘性，某些无状态 API 也可以轮换，不在程序里识别名称后强制模式。

新的对象关系：

```text
上游渠道 Source -> 静态库存 / API 临时候选
                         |
下游应用 Consumer -> 授权业务路由 RoutePolicy
                         |
                 mode = sticky / rotate
                      /             \
      会话绑定 SessionBinding       新分配 + 近期去重
                      \             /
                   验活 / 资格检查 / 交付
```

RoutePolicy 类似 Resin 的 Platform，但不是认证凭证。Consumer 才是认证和配额主体，策略只是它获准使用的路由范围及行为。

## 3. 粘性模式的明确契约

### 3.1 绑定键与身份保护

绑定主键按 `consumer_id + route_policy_id + session_key_hash` 确定。session_key 通常是业务账号或一段工作流 ID，由下游显式传入；它不是管理 Token、不是整把下游 Key，也不应直接拿真实业务 Authorization 明文存储。

不同消费者使用相同会话名互不影响。同一消费者轮换 API Key 后，仍能找到自己的绑定。限制键长度、创建速率、活跃会话数和总 TTL，避免无限会话占用容量。若需要域名隔离，在业务策略中定义固定 scope，不让调用方随意改 scope 绕过 CD。

`mode=sticky` 必须有会话键或已授权的明确默认键；缺失返回 `SESSION_KEY_REQUIRED`，不能悄悄走随机模式。第一版 sticky 取号限定 `count=1`，多个会话使用多次请求；不把“取五条”解释成五条都粘到同一个出口。

### 3.2 什么被固定

- `anchor=endpoint`：固定规范化连接参数及上游会话凭证，出口仍可能随连接变化。
- `anchor=exit_ip`：以本次实测出口为锚，后续交付必须再次核对；原节点失效时，可在授权范围内试探同出口替代节点。
- 上游若提供 session token，生成一次后绑定，验活和返回的连接必须使用同一 token，不能验活 A 会话却交付 B 会话。

“本次观察未变”与“上游承诺固定出口”分开显示。只有代理端点/上游会话有相应稳定能力，才接受要求上游保证的策略。普通会轮换的网关，即使反复返回同一 host:port，也不能声称固定出口。

当前 SCDN 适配器得到的是 host:port 和声明协议，没有证明固定出口或供应商会话 TTL 的字段。所以它可以提供端点绑定/观察级的尽力保持，但不能凭空宣称供应商级固定 IP 保证。请求硬要求而源能力不足时返回 `STICKY_CAPABILITY_UNSUPPORTED`，不静默降低要求。

### 3.3 首次与重复请求

首次请求在 SQLite 原子领取该会话的创建许可，网络取号和探测在事务外执行，通过后再原子提交绑定和容量租约。同一会话并发创建只能有一个生效版本，其他请求有界等待或返回进行中，不重复消耗供应商配额。

重复请求先找绑定，不再为了“API 渠道”重新向供应商取一份代理。在返回连接前，仍按当前严格契约执行属于本次取号请求的验活，并检查源启停、凭证、出口、到期和会话版本。绑定命中不是复用过期验活证据。

“每次取号重新验活”不等于“每个业务 HTTP 请求都要重新取号”。下游可以在会话有效期内使用已获连接执行业务；只是本服务无法持续知道这些业务请求是否成功。

### 3.4 期限、容量和故障

第一版采用固定 TTL，不因命中或同出口换节点而滑动续期。有效期限不得超过策略上限、对应容量租约上限、已知供应商到期或已知上游 sticky 会话期限。未知供应商寿命不改写成已保证寿命，响应明确返回 effective TTL 与保证级别。

一个活动粘性绑定拥有一份容量租约；重复访问复用自己的容量所有权，不再申请一个会被自己占用挡住的新槽位。第一版会话期限与这份租约期限对齐。显式释放会话或这份关联租约都会结束绑定；普通取号命中不增加占用。需要共享时遵守相应槽位上限，不承诺不同账号一定使用不同 IP。

故障策略独立配置：

| 策略 | 行为 |
| --- | --- |
| `same_exit_or_fail` | 原连接失效时先试同出口且满足能力的替代；无法保持则返回 `SESSION_UNAVAILABLE`，不换出口 |
| `rebind` | 先试同出口，仍失败才允许分配其他出口；必须返回 changed 原因和新 generation |

API 粘性模板默认 `same_exit_or_fail`。对未知结果的业务 POST，本服务不能以换代理为由替客户端重放业务请求；这里只管理取号。现有 TCP/CONNECT 连接也不能被无损搬到另一代理。

严格模板到期后明确返回 `SESSION_EXPIRED`，由调用者显式重新建立或按预先配置的到期策略处理；不能在不知道客户端意图时把过期当作“从未建立”，悄悄换出口。保存有限期终态元数据以识别这些情况，不无限保留敏感连接快照。

绑定使用 generation/owner fencing。慢的旧创建、旧探测或取消操作不能覆盖已经换新的绑定；请求过滤条件与现有绑定冲突时返回 `SESSION_CONSTRAINT_MISMATCH`，不静默重绑。会话释放、重绑与重试需要对象归属校验和幂等操作 ID。

## 4. API 不入池与粘性不冲突

原规划的“API 候选只属于一次请求”需要精确修订：**未分配的 API 候选只属于一次请求；已经交付并建立粘性绑定的连接，可以在会话私有状态中保留至到期。**

```text
API 首次取号 -> 本请求候选 -> 验活 -> 会话私有绑定
                               -> 未选中条目丢弃

同会话再次取号 -> 私有绑定 -> 本次验活 -> 返回同一绑定
```

该私有绑定保存加密连接快照、指纹、观察出口、源版本、上游 token 引用和期限，但不写入公共静态候选表、不被其他会话选择，也不参加库存预热和夜间扫描。会话释放/到期后按审计保留规则清理敏感快照，绝不能回收到池中。

同出口替代只能来自允许且合格的静态库存、本请求已有的 API 候选，或预算内明确允许的供应商调用。不能为了维持粘性偷偷在后台囤一批 API 代理。

## 5. 非粘性模式：随机和真正轮换不是一回事

Resin 的 random 模式是不保留账号绑定，仍可能连续选中同一节点，或者选中不同节点却具有相同出口。我们的爬虫模板要在此基础上增加分配历史。

`mode=rotate` 的建议契约：

- 每次新取号都执行新的选择，不查粘性绑定。
- `dedupe_by=connection` 排除近期已交付的同连接；`dedupe_by=exit_ip` 排除近期实测相同出口。
- 每批内部也按同一去重键去重；不同 host:port 若出口一样，在出口去重下只算一个。
- `cd>0` 定义时间窗口，保证窗口内不新分配同一键。`cd=0` 本身不保证上次 IP 不重现；爬虫模板若要求连续必换，还须至少保留上次成功出口排除规则。
- 只有完成本次验活才知道出口的候选，在最终事务中领取出口使用权；并发请求探到同出口只能按去重策略成功一个。
- 无新出口时返回 `ROTATION_EXHAUSTED`、有条件的重试时间或显式允许的部分批次；不放松去重、不静默复用旧 IP。

默认去重范围是消费者，不能通过换上游源、改路由名或换 Key 绕过。以后可支持固定的消费者+业务域范围，但必须是管理员定义的业务语义。

`on_exhausted=allow_repeat` 若需要，必须显式配置并在响应标记发生了降级；不作为“持续换 IP”模板的默认值。有限出口集合不可能无限不重复，供应规模与窗口内需求量必须匹配。

对于不支持稳定会话的轮换网关，本次探测的出口可能不同于下游下一条连接的出口。此时不能承诺实际业务请求级的严格出口去重；严格模板只使用能绑定到该观察出口的连接能力，否则拒绝或明确降为尽力模式。

## 6. CD 必须从“一律禁止重复返回”改为“限制新分配”

引入粘性后，旧规则“同消费者在 CD 内绝不再次拿到该代理”不能无条件套用，否则粘性第二次访问必然失败。

| 动作 | 业务 CD 行为 |
| --- | --- |
| 首次创建粘性绑定 | 属于新分配，检查并记录 CD |
| 同一未过期绑定命中 | 复用同一分配，可使用自己的 CD 记录；仍检查权限、健康、出口、容量所有权和期限 |
| 其他会话、rotate 请求或强制重绑 | 属于新分配，必须检查现有 CD；不能伪装成命中 |
| 同出口替代节点 | 仅对同一绑定进行受控替换；验证相同出口并原子转移容量，不延长原会话 TTL |
| 关闭/释放会话 | 释放绑定和容量，不清空仍有效的业务 CD |
| 改传 cd=0、换 Key、改 session_key | 不删除旧窗口，不允许新分配绕过旧窗口 |

CD 的 owner 以服务端绑定 ID/generation 识别，不能只相信调用者传了同名 session_key。抽象业务 session_key 不参与代理连接指纹计算；只有真正改变代理连接上下文的上游会话 token 才影响连接身份。否则每次换 session_key 就变出一个“新代理”，CD 会失效。

固定 CD 窗口从新分配的交付边界开始；命中同一分配不隐式延长窗口，也不改变绑定 TTL。若需要“会话结束后再冷却 N 秒”，另设 `post_session_cd` 策略，不与现有 cd 偷偷叠加。

权限、源禁用、硬过期和已确认故障优先于粘性复用。绑定记录和有效 CD 强事务持久化，内存可做索引，不学习 Resin 把这些关键状态当作允许丢失的缓存快照。

## 7. 目标接口示例

以下为规划示例，当前实现尚不接受这些新字段。消费者身份来自下游 Key，客户端只能使用管理员授权的 route。

API 粘性业务：

```json
{
  "count": 1,
  "route": "api-sticky",
  "mode": "sticky",
  "session_key": "account-42",
  "session_ttl_seconds": 300,
  "on_unavailable": "same_exit_or_fail"
}
```

该 route 配置 anchor 和所需保证级别；不能从这段示例推断任意免费代理已获得固定出口保证。

爬虫轮换：

```json
{
  "count": 5,
  "route": "crawler-rotate",
  "mode": "rotate",
  "dedupe_by": "exit_ip",
  "cd": 300,
  "on_exhausted": "fail"
}
```

响应在现有连接和验活信息之外增加：effective mode、绑定 ID/generation、是否复用、是否改变出口、保证级别和有效期限。业务可区分正常会话命中与明确重绑，不依赖解析自然语言消息。

新增按归属保护的会话状态、释放和重绑接口。重绑请求指定 expected generation 及幂等键，关闭会话不等于删除 CD。重绑失败或发送结果不明时保留明确状态和审计，不重复购买或默默切换旧结果。

## 8. 管理端需要怎样补充

上游渠道页面继续负责来源和拉取，不把粘性开关硬塞成渠道全局属性。它只补充能力展示：能否支持端点绑定、上游会话参数、出口稳定性的依据、供应商 TTL。

在下游应用内增加“业务路由”和“活动会话”子页：

- 路由：默认 sticky/rotate、允许源、优先级、协议/地区、是否允许请求覆盖模式。
- 粘性：会话键要求、anchor、TTL 上限、原出口不可用时的策略、到期策略、最大活动绑定数。
- 轮换：按连接/出口去重、CD、连续排除上次出口、耗尽处理和有限的批量上限。
- 会话：当前代理、最近观察出口、保证级别、来源、建立/到期、最后取号、命中次数、重绑原因。
- 操作：查看、释放、显式重绑；涉及出口变化时说明影响，不修改正在传输的连接。

指标区分 sticky 命中率、同出口恢复次数、被允许的出口变更、严格保持失败，以及 rotate 的实际出口去重率、窗口耗尽和降级次数。

## 9. 借鉴边界：不自动变成 Resin 那样的转发网关

当前项目是“返回代理给下游直接使用”。它可以在取号 API 层支持粘性和轮换，不必把业务流量转发到自己的服务器。

在此模式下，轮换粒度是**一次取号/新分配**。爬虫要每次业务请求换 IP，必须配合重新取号并使用相应连接，或者使用提供明确逐请求轮换能力的上游。拿到一个普通代理后一直复用客户端连接池，不会因为本服务配置 rotate 就自动变 IP。

若要像 Resin 一样“客户端永远连一个入口，服务透明选择出口”，需要单独增加数据面网关。这会让业务流量经过服务器，改变带宽、连接数、凭证保护和监控要求，不能作为本轮研究的隐式实现决定。

即使未来增加网关，HTTP CONNECT/SOCKS5 通常也只能在新隧道/新连接时选择出口。同一 TLS 隧道内的 HTTP/2、多请求复用不能在不终止连接或介入 TLS 的情况下逐请求换 IP；长连接和进行中的请求不能被无损迁移。

Resin 的目标域名被动延迟来自转发流量。本项目当前只能可靠获得自己的探测延迟和经过归属校验的下游反馈；P2C 可作为选点优化，但不能把 Judge 延迟包装成真实目标 API 延迟。可路由视图只是派生索引，未知观察候选仍需有有界探测入口，避免重现地区过滤冷启动问题。

## 10. 数据与实施增量

增加或调整的核心数据：

- `route_policies`：授权路由范围、mode、会话/轮换默认值及版本。
- `session_bindings`：consumer、route、会话键哈希、generation、状态、指纹、anchor、源/配置版本、上游会话引用、固定截止时间和关联容量租约。
- `consumer_usage`：新分配的连接/出口去重键、CD 到期、绑定 owner；无需依赖静态库存外键。
- 交付/验活记录：区分 new allocation、sticky reuse、same-exit replacement、rebind，以及 mode 和连续性变化。

会话绑定、容量租约、CD 及必要的交付状态在短事务中一致提交；网络验活在外部。进程恢复后重建索引、回收失效创建许可，不直接信任旧 PASS，也不因丢失内存状态就忘记已经发出的绑定。

实施顺序纳入主规划 M0/M2/M3/M4，而不是等管理页做完才加：先固定身份和模式契约，再修改表和交付边界，再实现两条模式及界面。Redis 仍不是必要依赖。

必须新增的验收场景：

| 场景 | 结果 |
| --- | --- |
| 同一会话连续取号 | 相同有效绑定、本次验活；无重复 API 拉取、无额外容量占用 |
| 同会话并发首次创建、重启后重复访问 | 只有一个生效绑定和一份必要上游操作；恢复不丢绑定/CD |
| 粘性请求缺会话键、约束冲突或 TTL 超限 | 明确拒绝，不静默随机或放宽条件 |
| 原节点失效但有可用同出口替代 | 验证出口后替换，TTL 不延长，旧操作无法覆盖新 generation |
| 严格粘性没有同出口可用 | 明确失败，绝不偷偷换出口 |
| 允许重绑 | 明示改变、更新 generation，遵守新分配 CD 和预算 |
| API 粘性保持到期 | 私有绑定可复用，公共库存始终零增长，终态不回池 |
| CD 内同会话命中与另开会话 | 自己可复用；新分配不能借会话名绕过 CD |
| 轮换连续取号及批量去重 | 按配置窗口和出口排除；不同端口同出口不能重复充数 |
| 多个请求同时验活到同出口 | 原子去重，不能同时成功发出被禁止的重复项 |
| CD 为零或仅一个可用出口 | 如要求连续必换仍排除上次出口；无新出口明确耗尽，不称随机即必换 |
| 上游旋转网关不支持粘性 token | 不承诺稳定出口和实际业务级严格去重 |
| 释放、强制重绑、Key 轮换、其他消费者同名 session | 归属和 CD 正确，不串会话、不复用旧 generation |
| 客户端复用长连接 | 文档和响应只承诺取号粒度，不声称服务已逐业务请求换 IP |

## 11. 本轮结论

采纳 Resin 的业务路由/账号分层、出口锚定、同出口恢复、配置版本保护和有界选点思路。针对本项目明确加强：显式模式、严格出口连续性选项、真正的轮换去重、会话复用与 CD 的兼容、API 私有绑定不入池，以及会话/租约/CD 的强持久化。

本轮只研究并更新规划，没有改应用代码、安装 Resin、修改密码、提交推送或部署。
